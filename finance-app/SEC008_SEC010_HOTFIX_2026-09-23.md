# SEC-008 + SEC-010 — минимальный production hotfix

Дата: **2026-09-23**. PR #99 и миграции 0086–0092 **не применялись**.
Изменение в production — ровно пять операторов: три `create or replace` хелперов
и два `revoke`. Финансовые данные не трогались.

Артефакты: `supabase/migrations/hotfix/SEC008_SEC010_hotfix.sql` (применённое),
`supabase/migrations/rollback/SEC008_SEC010_before.sql` (откат из фактического ACL
и фактических тел функций), `scripts/concurrency/sec010_test.sh` (регрессия).

## 1. Минимальный dependency scope (read-only, до изменения)

### Хелперы в RLS — 194 политики схемы `public`

| Хелпер | Политик | Таблиц |
|---|---|---|
| `can_edit_finance` | **110** | 50 |
| `can_manage_team` | 8 | — |
| `can_write_tx` | 3 | — |
| `is_team_member` | 50 | — |
| `current_team_role` | 8 | — |

**Изменение NULL → false для RLS семантически нулевое.** Политика пропускает строку
только при `true`; `NULL` и `false` одинаково означают отказ. Ни одна из 194 политик
не может изменить поведение.

### Хелперы в SECURITY DEFINER функциях

Опасная форма — `if not public.can_*(...) then raise` — ровно в **6** функциях
(именно они и страдали от SEC-008):
`support_open_period`, `support_delete_period`, `merge_counterparties`,
`materialize_auto_accruals`, `materialize_support_cycles`, `academy_assign`.
Для них NULL → false — это и есть исправление.

Ещё 2 функции используют хелперы как выражение, а не как guard:

* `vault_directory(uuid)` — `can_edit_finance` попадает в `case when f.rv or f.mg then … else '' end`. При NULL: `false or NULL` = NULL → ветка `else`; при false: `false or false` = false → та же ветка `else`. Результат идентичен.
* `vault_can_reveal(uuid)` — `can_manage_team` внутри `exists(... where A or B or …)`. В `WHERE` и NULL, и false отбрасывают строку. Результат идентичен.

### Обычные RPC и код приложения

В `src/**` прямых обращений к `can_edit_finance` / `can_write_tx` / `can_manage_team`
нет вовсе — приложение пользуется собственной TS-функцией `canEditFinance(role)`
из `@/lib/team`. Зависимости от NULL-семантики в коде нет.

### Кто вызывает 6 guard-функций — проверено по коду, не угадано

| Функция | Вызывающий | Клиент | Роль БД |
|---|---|---|---|
| `support_open_period` | `src/components/SupportPeriods.tsx:66` | `@/lib/supabase/client` | **authenticated** |
| `support_delete_period` | `src/components/SupportPeriods.tsx:109` | `@/lib/supabase/client` | **authenticated** |
| `merge_counterparties` | `CounterpartiesTable.tsx:71`, `DuplicateSuggestions.tsx:35` | `@/lib/supabase/client` | **authenticated** |
| `academy_assign` | `academy/AssignmentPanel.tsx:59` | `@/lib/supabase/client` | **authenticated** |
| `materialize_auto_accruals` | `api/payroll/materialize/route.ts:22` | `@/lib/supabase/server` | **authenticated** (сессия пользователя) |
| `materialize_support_cycles` | `api/payroll/materialize/route.ts:24` | `@/lib/supabase/server` | **authenticated** (сессия пользователя) |

**Ни одна не вызывается через `@/lib/supabase/admin` (service_role) и ни одна не
вызывается кроном.** У каждого вызывающего есть настоящий `auth.uid()`, а для
настоящего участника команды хелпер и раньше возвращал `true`/`false` — для
легитимных сценариев не меняется ничего.

Единственное изменение поведения: вызов `support_*` от `service_role` **без**
пользовательского JWT раньше молча проходил (NULL), теперь получает `forbidden`.
Таких вызывающих в коде нет. Это то же поведение, что даёт миграция 0091.

## 2. SEC-008 hotfix

Применена **дословно ЧАСТЬ A миграции 0091**, альтернативной реализации не писал:
`can_edit_finance`, `can_write_tx`, `can_manage_team` переписаны на `exists (...)`.

Проверка на production, 12:49:24 UTC, чужая команда:

| Хелпер | Значение | `is null` |
|---|---|---|
| `can_edit_finance` | **false** | false |
| `can_write_tx` | **false** | false |
| `can_manage_team` | **false** | false |

Инвариант «не-участник → false, никогда NULL» выполнен.

`create or replace` сохраняет привилегии — ACL хелперов не изменился
(`{postgres, authenticated, service_role}`), `owner`, `security definer` и
`search_path=public` тоже.

**Идемпотентность относительно будущего 0091.** ЧАСТЬ A — `create or replace` с
дословно тем же телом: повторное применение — no-op. ЧАСТЬ B — `revoke`
отсутствующего гранта — no-op; 0091 снимает те же гранты с тех же двух функций и
затем возвращает `authenticated` на `support_delete_period`, что совпадает с
состоянием после hotfix. Проверено исполнением: после hotfix прогнан сам hotfix
повторно, затем 0091 — поведение всех пяти вызывающих не изменилось.

## 3. SEC-010 — привилегии

ACL **до** (сохранён в артефакте отката):

```
support_open_period(uuid,bigint,uuid,uuid)  {=X/postgres,postgres=X,anon=X,authenticated=X,service_role=X}
support_delete_period(uuid)                 {=X/postgres,postgres=X,anon=X,authenticated=X,service_role=X}
```

Применено:

```sql
revoke execute on function public.support_open_period(uuid, bigint, uuid, uuid) from anon, public;
revoke execute on function public.support_delete_period(uuid) from anon, public;
```

`authenticated` **сохранён** — подтверждено по коду: `SupportPeriods.tsx` вызывает
обе RPC браузерным клиентом, то есть непосредственно от `authenticated`. Минимальный
ACL `{postgres, service_role}` здесь неприменим — он сломал бы рабочий сценарий.
Авторизация внутри функций после ЧАСТИ A корректна: не-участник получает `forbidden`.

ACL **после**, проверено 12:49:24 UTC:

```
support_open_period(uuid,bigint,uuid,uuid)  {postgres=X/postgres,authenticated=X/postgres,service_role=X/postgres}
support_delete_period(uuid)                 {postgres=X/postgres,authenticated=X/postgres,service_role=X/postgres}

has_function_privilege: anon = false ✅  PUBLIC = false ✅  authenticated = true  service_role = true
```

`owner = postgres`, `security definer = true`, `search_path = public` — не менялись.
Тела функций не менялись.

## 4. Проверка без разрушающих вызовов на production

**`support_open_period` и `support_delete_period` на production не вызывались.**
Доказательства — каталоги (§2, §3) и регрессия на одноразовой БД.

```

```

Включая `SEC-008 support_open_period — посторонний получает отказ` и контроль
«данные команды B не изменились».

### Новая регрессия `scripts/concurrency/sec010_test.sh` — 21/21 PASS

Production-образные `support_open_period(uuid,bigint,uuid,uuid)` и
`support_delete_period(uuid)` с тем же guard'ом и тем же исходным ACL; прогон
BEFORE → применение файла hotfix → AFTER → повторное применение hotfix и 0091.

| Вызывающий | BEFORE | AFTER |
|---|---|---|
| C1 `anon` | **allowed** — период и обязательство созданы (уязвимость воспроизведена) | **denied_privilege** — `permission denied for function` |
| C2 `authenticated`, не участник | **allowed** (уязвимость воспроизведена) | **forbidden** |
| C3 `authenticated`, участник без права финансов (viewer) | forbidden | forbidden |
| C4 `authenticated`, участник с правом финансов | allowed | **allowed** — рабочий сценарий сохранён |
| C5 `service_role` без пользователя | allowed | **forbidden** (ожидаемое ужесточение, вызывающих нет) |

Данные: BEFORE 0 → 4 периода и 0 → 4 обязательства (четыре прошедших вызова);
AFTER 4 → 5 (прошёл только C4); фаза идемпотентности 0 → 1 (снова только C4).

Дополнительно проверено на одноразовой БД: `can_edit_finance`/`can_write_tx`/
`can_manage_team` для чужой команды = `false` (не NULL), для владельца = `true`,
для viewer = `false`.

Дефект самого теста, найденный и исправленный по ходу: первичный разбор ответа
считал успехом любую строку с подстрокой `period`, а её содержит имя индекса
`project_periods_project_month_uniq`, из-за чего unique-violation засчитывался как
успешный вызов. Разбор переписан: ошибки проверяются раньше успеха. Первый прогон
с этим дефектом показывал ложный PASS — цифры в таблице выше сняты после исправления.

## 6. Повторный blocker scan

Критерий: `SECURITY DEFINER` + доступ клиента + (финансовая запись/удаление ИЛИ
Vault ИЛИ внешний HTTP). LOW/MEDIUM не расширял.

Доступных `anon` или через `PUBLIC` и при этом пишущих — осталось **две**, обе вне критерия:

| Функция | anon/PUBLIC | Пишет | Финансы | Vault | HTTP | Вердикт |
|---|---|---|---|---|---|---|
| `assess_public_submit(text,jsonb)` | да | `assess_answers`/`scores` | нет | нет | нет | анонимна по share-токену — так задумано |
| `vault_request_access(uuid)` | да | только `notifications` | нет | нет (секретов не читает) | нет | guard `is_team_member` возвращает `false` — защита держится |

**Функций с `anon`/`PUBLIC` + финансовой записью, Vault-секретами или внешним HTTP
не осталось — ноль.** Остальные 11 пишущих SECURITY DEFINER доступны только
`authenticated`, это штатная поверхность приложения, и их guard'ы после ЧАСТИ A работают.

**Security gate перед PR #99 считаю пройденным.**

## 7. SEC-011 — не трогал, зафиксировано на потом

`next_document_number(uuid,text,text)` и `next_project_code(uuid)`:
`SECURITY DEFINER` **без закреплённого `search_path`**, EXECUTE у `anon`/`PUBLIC`,
обе только читают. Remediation отдельным hardening-изменением **после** развёртывания:

1. `alter function … set search_path = public`;
2. явные гранты: снять `anon`/`PUBLIC`, оставить `authenticated`/`service_role`;
3. проверить, нужен ли им `SECURITY DEFINER` вообще — если читают только свои же
   таблицы под RLS вызывающего, режим можно убрать.

Отдельно: в 0091 ЧАСТЬ B перечислены **несуществующие** сигнатуры
`next_document_number(uuid, text)` и `bybit_sync_logged()` (фактические —
`(uuid,text,text)` и `(integer)`), их `revoke` уходит в ветку `undefined_function`
и молча пропускается. На SEC-008/010 это не влияет (там сигнатуры верные),
SEC-009 уже закрыт отдельно, но при hardening SEC-011 сигнатуры надо поправить.
