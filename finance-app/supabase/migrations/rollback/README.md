# Откат миграций 0086–0091

Скрипты отката **не для «просто на всякий случай»**: сначала смотри
`PRODUCTION_DEPLOY_RUNBOOK.md` → «Критерии откатa». Порядок отката всегда
обратный порядку применения: `0091 → 0090 → 0089 → 0088 → 0087 → 0086`.

## Совместимость со старым кодом приложения

| Миграция | Схема совместима со СТАРЫМ кодом | Требуется согласованный откат приложения |
|---|---|---|
| 0086 | **да** (только новые ограничения; старый код работает, но может получить ошибку 23505/23514 там, где раньше молча портил данные) | нет |
| 0087 | **да** (сигнатуры функций не менялись; добавлена колонка с default) | нет |
| 0088 | **да** (только новые таблицы и функции) | нет |
| 0089 | **да** (новые колонки + триггеры; старый код пишет строку целиком, триггер сам двигает version) | нет |
| 0090 | **да** (только новые колонки/индексы/таблица/функции; старый импорт по-прежнему дедупит по `source`+`external_id`) | нет |
| 0091 | **да** (`can_*` стали строже — это исправление дыры; REVOKE снимает лишние гранты у anon/PUBLIC) | нет |

**Обратное направление несовместимо:** НОВЫЙ код приложения требует наличия
RPC из 0088–0091 и колонки `transactions.version`. Поэтому:

* деплой: **сначала миграции, потом код**;
* откат: **сначала код (предыдущий деплой Vercel), потом, если действительно
  нужно, миграции**. Откатывать миграции при работающем новом коде нельзя —
  сохранение операций, инвойсов и импорт сразу перестанут работать.

## Что откат НЕ восстанавливает

`0087_down` и `0090_down` не возвращают значения `origin`, `bank_provider*`
в прежнее состояние — они просто удаляют эти колонки вместе с данными
классификации. Финансовые поля (сумма, дата, счёт, тип, валюта, связи) миграции
не меняли, поэтому после отката финансовые данные остаются ровно теми же.
Строки, созданные новым кодом (в т.ч. `bank_reconciliation_conflicts`), после
отката 0090 пропадут вместе с таблицей — выгрузи её заранее, если конфликты уже
разбирались.
