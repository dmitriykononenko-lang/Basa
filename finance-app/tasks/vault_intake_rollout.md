# Выкладка «Запросить доступ у клиента» (ветка `claude/vault-client-intake`)

Каждый шаг с пометкой **«да»** выполняется только после отдельного «да» Дмитрия на этот шаг.
Значения ключей и паролей нигде не выводятся. `VAULT_KEY` не меняется.

Проверено 18.11 (только чтение production): ограничения `vault_access_log_action_check` и
`notifications_type_check`, сигнатура `vault_directory`, `pgcrypto` в `extensions` — ровно такие,
как ожидает 0101. Конфликтов с 0100_amo_link (ветка `claude/amo-invoice-link`) нет: номер 0101,
объекты не пересекаются.

## 0. Ревью и слияние — **«да»**
- Ревью diff `main...claude/vault-client-intake`; слияние в `main` (без push до «да»).

## 1. Переменные окружения Vercel (Production) — **«да»**
| Переменная | Значение | Зачем |
|---|---|---|
| `INTAKE_HOST` | `access.koagency.me` | на этом хосте доступны только `/a` и `/api/intake/*` |
| `INTAKE_BASE_URL` | `https://access.koagency.me` | из этого адреса собирается ссылка клиенту |
| `INTAKE_AGENCY_EMAIL` | `koagency.me@gmail.com` | кого клиент добавляет пользователем |
| `INTAKE_META_BUSINESS_ID` | ID бизнес-портфолио KO (если есть) | инструкция «Добавить партнёра» в Meta |
| `INTAKE_GOOGLE_MANAGER_ID` | ID MCC KO (если есть) | привязка Google Ads к управляющему аккаунту |
| `NEXT_PUBLIC_SITE_URL` | `https://basefinance.pro` (проверить, что задан) | ссылки в уведомлениях ведут в Basa |

Уже должны быть (проверить только наличие, не значения): `SUPABASE_SERVICE_ROLE_KEY` (письма/Telegram),
`RESEND_API_KEY` + `EMAIL_FROM` (письмо), `TELEGRAM_BOT_TOKEN` (Telegram), `CRON_SECRET` (крон), `VAULT_KEY`.
Без любого из первых четырёх фича работает, но соответствующий канал молча пропускается (колокольчик есть всегда).

## 2. Миграция 0101 в production — **«да»**
1. Бэкап по `BACKUP_RUNBOOK_MACOS.md` (пароль бэкапа вводит Дмитрий во вкладке терминала).
2. Репетиция на production в откатываемой транзакции: `begin; \i 0101_vault_intake.sql; <проверки>; rollback;`.
3. «да» → применить `0101_vault_intake.sql`.
4. Проверки: `has_function_privilege('anon', …)` — `t` только у `vault_intake_load/submit`;
   `select * from vault_directory('<team>') limit 1` у владельца; таблицы пустые.
5. Откат при необходимости: `supabase/migrations/rollback/0101_vault_intake_down.sql` (проверен локально: down → up).

Порядок: сначала миграция, потом деплой. Старый код с новой БД работает (лишние колонки
`vault_directory` он игнорирует); новый код без миграции — нет.

## 3. Деплой — **«да»**
- Слияние в `main` → автодеплой Vercel (или ручной promote превью). Новый крон `/api/cron/vault-intake` раз в сутки.

## 4. Домен access.koagency.me — **«да»**
- Vercel → проект Basa → Domains → `access.koagency.me`.
- DNS koagency.me (Beget): `CNAME access → cname.vercel-dns.com` (точное значение показывает Vercel).
- Проверка: `https://access.koagency.me/a` открывает страницу клиента; `https://access.koagency.me/dashboard` → 404.

## 5. Ключ команды — делает Дмитрий сам
- Basa → Пароли → «Создать ключ команды». Пароль ключа вводит и хранит только Дмитрий
  (личный менеджер паролей). Он не восстанавливается.

## 6. Пробный запрос
- «Запросить доступ у клиента» → сервис «Другой», тестовые данные → открыть ссылку с телефона →
  отправить → уведомления (колокольчик, письмо, Telegram) → «Принять» → проверить запись → удалить тестовую запись.

## 7. Запуск с клиентами
- Первые: 7S и Maison (пароли были в чатах): сначала клиент меняет засвеченный пароль, затем передаёт
  новый по ссылке; для amo/Kommo — добавляет нас пользователем.
- Сообщение клиенту копируется из окна ссылки (кнопка «Копировать сообщение клиенту»).

## Откат
- Деплой: promote предыдущего деплоя в Vercel.
- БД: `rollback/0101_vault_intake_down.sql` (удаляет запросы, ключ команды и привязку записей к контрагенту;
  принятые записи парольницы остаются).
