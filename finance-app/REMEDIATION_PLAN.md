# REMEDIATION_PLAN.md — архитектура исправлений

> **Статус:** шаги 0–5 реализованы в коде и миграциях и протестированы на одноразовом
> локальном Postgres — см. **`REMEDIATION_STEP0_5.md`** (таблица
> `Finding | Before test | Fix | After test | DB guarantee | Remaining risk`, список
> миграций и RPC к применению). К production ничего не применялось.
> Шаги 6–9 (историческая чистка FIN-03, валюта, SEC-001/002, CI) — не начаты.

Дата 2026-09-22. Ничего не реализовано, production не изменялся, исторические данные не тронуты.
Документ описывает, **как** надо исправлять, и **в каком порядке**. Источники: `E2E_AUDIT.md`
(потоки и тесты T1–T9), `FIN03_FORENSICS.md` (forensic по FIN-03), `SECURITY_AND_INTEGRITY_AUDIT.md`.

Принципы, заданные заказчиком и принятые как обязательные:

1. **Одна бизнес-операция = одна атомарная транзакция БД.** Если операция трогает больше одной
   записи — она обязана выполняться внутри одной транзакции, то есть внутри RPC-функции
   (у Supabase JS клиентских транзакций нет — это установленный факт, см. `E2E_AUDIT.md` §1).
2. **Race condition не маскируется frontend-локом.** Существующие `busy`/`setBusy`/`disabled`
   остаются исключительно как UX и в состав исправления не входят: они не действуют между
   вкладками, устройствами, пользователями и повторными запросами.
3. **Инвариант, который можно выразить в схеме, выражается в схеме.** Проверка в приложении —
   вторая линия, а не первая.

## 2. Архитектура исправления по каждому сценарию

Обозначения: **RPC** = `SECURITY DEFINER` функция с `set search_path = public`, вся функция —
одна транзакция. **CT** = `CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED` (проверка на
COMMIT — единственный способ выразить агрегатный инвариант, `CHECK` агрегаты не умеет).

### T1 — начисление ЗП (CRITICAL)

Сейчас: `/payroll/page.tsx:58-59` вызывает `materialize_auto_accruals()` и
`materialize_support_cycles()` **при рендере GET-страницы**; внутри — `if not exists(...) then
insert` без уникального индекса.

Исправление:
1. **Убрать запись из рендера.** Страница становится read-only. Материализация — либо кнопкой
   (POST-роут), либо ночным cron'ом `/api/cron/recurring`. Это же снимает проблему prefetch/refresh.
2. **Идемпотентность в схеме.** Добавить `obligations.origin text not null default 'manual'`
   (`'auto'` для авто-начислений, backfill по `note like 'Начисление ЗП%(авто)'`), затем
   ```sql
   create unique index obligations_auto_accrual_uniq
     on obligations (counterparty_id, type, pay_part, period_month)
     where origin = 'auto' and period_month is not null;
   ```
   Дискриминатор `origin` обязателен: в проде уже есть законная пара «авто + ручное начисление»
   за один месяц (см. `db_integrity_audit.sql`), её ломать нельзя.
3. **`insert ... on conflict do nothing`** вместо `if not exists` внутри функции — проверка и
   вставка становятся одним атомарным оператором.
4. **Сериализация прогона:** `perform pg_advisory_xact_lock(hashtext('accrual:'||p_team::text))`
   первой строкой функции — два одновременных прогона по одной команде выстраиваются в очередь.
   То же для `materialize_support_cycles` (`support_open_period` в цикле).

### T2 / T3 — сохранение инвойса (HIGH / MEDIUM)

Сейчас: `api/invoices/route.ts:102-118` — три независимых запроса (`update invoices`,
`delete invoice_items`, `insert invoice_items`).

Исправление:
1. **RPC `invoice_save(p_payload jsonb) returns uuid`** — весь цикл в одной транзакции:
   `select ... for update` на строке инвойса (при обновлении) → delete позиций → insert позиций →
   пересчёт итогов. Роут оставляет за собой только zod-валидацию и проверку роли.
2. **Итог считается в БД, а не передаётся клиентом.** Триггер
   `after insert/update/delete on invoice_items for each statement` пересчитывает
   `invoices.amount` и `invoices.vat_amount` из позиций → инвариант «сумма = Σ позиций»
   выполняется **по построению**, а не проверкой.
3. **CT-страховка** на случай ручного вмешательства:
   `Σ invoice_items.amount = invoices.amount` (deferrable initially deferred) — разрешает
   промежуточное состояние внутри транзакции и запрещает его на COMMIT.
4. T3 закрывается пунктом 1 автоматически: сбой на вставке позиций откатывает и изменение инвойса.

### T5 — номер инвойса (MEDIUM)

1. ```sql
   create unique index invoices_team_number_uniq on invoices (team_id, number)
     where coalesce(number,'') <> '';
   ```
   Безопасно: текущих дублей 0 (проверено).
2. **Атомарная выдача номера.** Таблица-счётчик `invoice_counters(team_id, project_nnn, last_no,
   primary key (team_id, project_nnn))` и выдача одним оператором:
   ```sql
   insert into invoice_counters as c (team_id, project_nnn, last_no) values (_team, _nnn, 1)
   on conflict (team_id, project_nnn) do update set last_no = c.last_no + 1
   returning last_no;
   ```
   Вместо «`select max(...)` → `+1` → `insert`». Выполняется внутри `invoice_save`.
3. Ретрай на `unique_violation` (23505) — один повтор с новым номером.

### T4 — разнесение выплаты (HIGH)

1. **RPC `obligation_allocate(p_obligation uuid, p_tx uuid, p_amount bigint, p_request_id uuid)`**:
   ```
   select amount, currency from obligations where id = p_obligation for update;  -- блокировка строки
   select coalesce(sum(amount),0) from obligation_payments where obligation_id = p_obligation;
   if paid + p_amount > amount then raise exception 'переплата'; end if;
   insert into obligation_payments (...) values (...);
   ```
   `FOR UPDATE` сериализует конкурентные разнесения по одному обязательству.
2. **CT-инвариант в схеме:** `Σ obligation_payments.amount ≤ obligations.amount`
   (deferrable initially deferred) — закрывает и ручные правки, и любой обход RPC.
3. **Второй инвариант:** `Σ разнесений транзакции ≤ сумма транзакции`. Требует валюты —
   выполнять после FIN-02 (колонки `currency`/`rate`/`amount_base` в `obligation_payments`).
4. **Idempotency key** `p_request_id`: `insert into operation_requests(request_id) values (...)`
   первой строкой; повторная отправка той же формы (double submit, ретрай после таймаута)
   падает на первичном ключе и не создаёт второй платёж.
5. Клиентский лимит в `AllocatePaymentButton` остаётся, но только как подсказка в UI.

### T6 / T7 — импорт Точки и тротлинг (MEDIUM / LOW)

1. **`on conflict do nothing` вместо падения батча:**
   ```js
   .upsert(rows, { onConflict: 'team_id,source,external_id', ignoreDuplicates: true })
   ```
   Гонка перестаёт стоить импорт целиком: пересечение молча пропускается, новое вставляется.
2. **Батч + операции + контрагенты — один RPC** `tochka_import_commit(p_batch jsonb, p_rows jsonb)`.
   Это убирает ручную компенсацию `delete import_batches` (`tochka-import.ts:143`), осиротевшие
   батчи (сейчас 32) и осиротевших контрагентов (сейчас 18), созданных до неудачной вставки.
3. **Тротлинг — compare-and-swap одним оператором** вместо «прочитал → сравнил в JS → записал»:
   ```sql
   update bank_connections set last_synced_at = now()
    where team_id = _t and provider = 'tochka'
      and (last_synced_at is null or last_synced_at < now() - interval '2 hours')
   returning id;   -- 0 строк => чужой синк уже идёт, выходим
   ```
4. Для дополнительной защиты от параллельных прогонов cron и авто-синка:
   `pg_try_advisory_lock(hashtext('tochka:'||team_id))`, выход при неудаче.

### T8 — правка операции (HIGH)

1. **Оптимистичная блокировка.** `transactions` не имеет ни `updated_at`, ни версии. Добавить
   `version bigint not null default 1` + `before update` триггер `new.version = old.version + 1`.
   Клиент отправляет загруженную версию:
   `update transactions set ... where id = ? and version = ?` → `0 строк` → показать
   «операцию изменил другой пользователь, обновите страницу» вместо тихого затирания.
2. **Правка операции и её части — одна транзакция.** Сейчас `OperationCard.tsx:152` обновляет
   строку, а `partsRef.current.commit()` (ещё два запроса) выполняется **после**. Объединить в
   RPC `transaction_save(p_tx jsonb, p_parts jsonb, p_version bigint)`.
3. **CT-инвариант:** `Σ transaction_splits = transactions.amount` (или 0 строк) — закрывает CONC-08.

### T9 — split и склейка (CRITICAL)

1. **RPC `transaction_split(p_tx uuid, p_parts jsonb, p_request_id uuid)`**: `for update` на
   исходной строке → проверка `Σ частей = amount` → insert частей → перенос вложений →
   delete исходной. Сбой на любом шаге откатывает всё; двойное отражение денег невозможно.
2. **RPC `transactions_merge_transfer(p_expense uuid, p_income uuid, p_request_id uuid)`** и
   **`transaction_match_planned(p_plan uuid, p_actual uuid, p_request_id uuid)`** — по той же схеме
   (сейчас `OperationsTable.tsx:90-102` и `:162-164`).
3. **Idempotency key** обязателен: это операции «создать и удалить», повтор которых удваивает деньги.
4. Отдельно: `delete` в этих потоках сейчас не проверяет число затронутых строк. В RPC —
   `if not found then raise exception` (в тесте T9 удаление «потерялось» молча, вернув 0 строк).

### FIN-01 / FIN-02 — валюта (HIGH / MEDIUM)

1. `toBase()` не должен молча возвращать 1:1. Возвращать `null` и отображать явное
   предупреждение; вызвать наконец `missingRates()` (написан, но не используется).
2. История курсов: `unique (team_id, currency, rate_date)`, выбор курса
   `where rate_date <= transaction.occurred_on order by rate_date desc limit 1` — конвертация
   по курсу на дату операции, а не по последнему.
3. `obligation_payments`: добавить `currency`, `rate`, `amount_base` — сумма разнесения перестаёт
   «плавать» вместе с курсом (сейчас `unallocated.ts:83-85` пересчитывает остаток на «сейчас»).

### FIN-03 — устранение первопричины (HIGH)

Исторические данные — в §4. Здесь только то, без чего дубли вернутся:

1. **CSV-импортёры обязаны заполнять `source` и `external_id`.** Сейчас `StatementImportWizard.tsx`
   и `ImportWizard.tsx` не заполняют ни одно из полей (grep: 0 совпадений) — именно поэтому
   дедуп Точки их не видит. `external_id` — детерминированный хеш
   (`date|amount|currency|account|описание`), `source` — `'csv'`. Тогда уникальный индекс
   `transactions_source_external_uidx` начинает защищать и повторный импорт того же файла.
2. **Кросс-источниковая сверка при импорте.** Перед вставкой искать существующие строки по
   `(team_id, account_id, occurred_on, amount, currency)` **без фильтра по `source`** и требовать
   явного решения пользователя (пропустить / связать / всё равно создать). В `ImportWizard` такой
   режим есть (reconcile), в `StatementImportWizard` — нет.
3. **Единая трактовка перевода.** Первопричина формы дубля: Точка склеивает внутренний перевод в
   одну строку `transfer`, а сводный CSV пишет две строки (`expense`+`income`) — «переводы не
   склеиваются» прямо в note батча. Трактовка должна быть одна.
4. **Оставить один визард импорта** из двух сосуществующих.
5. Инвариант «одно экономическое событие — одна проводка» ограничением БД не выражается.
   Поэтому детектор FIN-03 остаётся в `scripts/db_integrity_audit.sql` и ставится в CI/cron как
   PASS/FAIL-гейт.

## 4. Безопасный план исправления исторических данных (FIN-03)

Dry-run: **`scripts/fin03/dry_run_remediation.sql`** — ни одного DML, только
`BEFORE → proposed → AFTER` и контрольные суммы. Реальные DELETE/UPDATE лежат в конце файла
**закомментированными**.

### Что предлагается и почему именно так

Удаляются **CSV-ноги** (126 `expense` + 126 `income` = 252 строки из `svodnaya_vypiska_2025.csv`),
банковская строка `type='transfer'` остаётся.

Обратный вариант — удалить банковскую строку — **недопустим**: дедуп Точки работает по
`(team_id, source, external_id)`, удалённая строка не будет найдена при следующем синке того же
периода и **вернётся обратно**.

### Контрольные суммы dry-run (проверены на production, только SELECT)

| Метрика | BEFORE | AFTER | Ожидание |
|---|---:|---:|---|
| Строк к удалению | — | 252 | ровно 252 |
| Объём удаляемых проводок | — | 241 099 418 | = 2 × 120 549 709 |
| Общий cash, RUB | 8 345 957 | 8 345 957 | **не меняется** |
| Выручка ОПиУ янв–мар 2025 | 175 193 002 | 54 643 293 | падение ровно на 120 549 709 |
| Детектор FIN-03 | 126 | 0 | 0 |
| Остатки 9 счетов | см. `FIN03_FORENSICS.md` §2.1 | сдвигаются на величину искажения | **требует решения по `opening_balance`** |

### Обязательное условие: `opening_balance` и удаление дублей — одно движение

У всех девяти затронутых счетов `opening_balance` примерно равен минус искажению
(`FIN03_FORENSICS.md` §2.3): похоже, остатки уже выравнивали плагом. Если удалить дубли и не
тронуть `opening_balance`, сегодня корректно выглядящие остатки поедут на суммы из §2.1
(например, «Фонд ФОТ Команда»: +442,19 ₽ → −443 688,34 ₽).

Поэтому перед удалением требуется **решение владельца данных**: являются ли отрицательные
`opening_balance` «Фондов» реальным входящим сальдо или компенсацией FIN-03. Правильный вход —
сверка с банковскими выписками на 2025-01-01. Блок 2b dry-run'а печатает поправку, при которой
видимые остатки не изменятся, но она **не является бухгалтерской истиной**.

### Порядок исполнения (только после письменного подтверждения)

1. Свежая PITR-точка / бэкап Supabase.
2. Остановить импорты (отключить `tochka-autosync` pg_cron и Vercel-cron) — чтобы набор не поехал.
3. Прогнать dry-run, сверить все контрольные суммы и список из блока 2a.
4. Получить подтверждение по списку 252 строк **и** решение по `opening_balance`.
5. Одна транзакция: архив → guard (ровно 252, ни одной банковской строки, ни одной зависимости) →
   `delete` → поправка `opening_balance` → `db_integrity_audit.sql` внутри той же транзакции →
   `commit` только если всё сошлось.
6. Сначала исправить причину (§2 FIN-03) — иначе повторный CSV-импорт создаст дубли заново.

### Rollback strategy

| Уровень | Механизм | Что восстанавливает | Ограничение |
|---|---|---|---|
| 1. Транзакция | весь шаг 5 в одной транзакции; `rollback` вместо `commit` | всё | пока не сделан commit |
| 2. Архивная таблица | `fin03_removed_transactions` — полная копия 252 строк с `archived_at` и `reason`, заполняется **до** удаления, **в той же транзакции** | `insert into transactions select <колонки> from fin03_removed_transactions` — строки возвращаются с **теми же id**, поэтому все ссылки (их сейчас 0) остаются валидными | требует обратной правки `opening_balance` тем же движением |
| 3. `opening_balance` | значения BEFORE напечатаны в блоке 2b dry-run'а и в `FIN03_FORENSICS.md` §2.3 | входящие остатки | фиксировать до начала |
| 4. PITR Supabase | точка восстановления перед шагом 5 | всю БД | теряются любые изменения, сделанные пользователями после точки |

Проверка успешности rollback: `db_integrity_audit.sql` снова показывает
`double-counted transfers (FIN-03) = 126`, общий cash = 8 345 957, выручка I кв. 2025 = 175 193 002.

## 6. Чего этот план НЕ делает

- Не реализован ни один пункт. Production не изменялся, исторические данные не тронуты.
- Не предлагается `DELETE`/`UPDATE` ни для одного класса, кроме **CONFIRMED_DUPLICATE**
  (PROBABLE/UNKNOWN отсутствуют — таких случаев 0).
- Не предлагается решение по `opening_balance`: это вопрос сверки с банком, а не кода.
- Не проверялись через браузер интерфейсные последствия правок (нет учётных данных, активные
  действия на production запрещены).
