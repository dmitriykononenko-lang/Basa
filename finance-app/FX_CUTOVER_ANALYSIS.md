# FX_CUTOVER_ANALYSIS.md — курсы валют: анализ и архитектура (FIN-01 / FIN-02)

Дата 2026-09-23. **Только анализ.** Ничего не реализовано, production не изменён,
PR #99 не расширен. Все цифры получены `SELECT`-запросами к production.

Целевое бизнес-правило (подтверждено заказчиком):

* cutover date = **2026-08-20**;
* для операций с `occurred_on >= 2026-08-20` управленческая стоимость считается по
  **официальному курсу ЦБ РФ, действующему на дату операции**;
* `USDT` → `1 USDT = 1 USD` → курс USD/RUB ЦБ на дату операции
  (`fx_method = USDT_USD_1_TO_1_CBR`);
* `USD` → курс USD/RUB ЦБ; `RUB` → курс 1;
* **никакого молчаливого `1:1`**: нет курса → `FX_RATE_MISSING`;
* исторический отчёт не должен меняться от того, что сегодня обновили курсы;
* split не применяет FX повторно — части наследуют курс исходной операции.

## 1. CURRENT FX ARCHITECTURE

### 1.1 Где хранится курс

| Объект | Что это | Факт |
|---|---|---|
| `public.fx_rates` | единственное хранилище курсов | колонки `team_id, currency, rate, rate_date`; PK `(team_id, currency, rate_date)`; FK `currency → currencies(code)`; RLS: 4 политики |
| семантика `rate` | «1 единица валюты = `rate` единиц базовой валюты» | базовая валюта команды — `teams.base_currency`, у обеих команд **RUB** |
| семантика `rate_date` | **дата ввода курса**, а не дата, на которую курс действует | `RatesEditor.save()` пишет `rate_date = сегодня` |
| **фактическое содержимое** | — | **одна строка на всю базу**: `USDT = 80.00000000, rate_date = 2026-06-16` |
| `public.currencies` | справочник допустимых кодов | `CNY, EUR, GBP, KZT, RUB, UAH, USD, USDT` |
| хранение результата пересчёта | — | **не хранится нигде**: ни `base_amount`, ни `fx_rate`, ни `fx_source` ни на одной таблице |

Кто пишет в `fx_rates`: **только** `RatesEditor` (ручной ввод, `upsert` с
`onConflict: team_id,currency,rate_date`). Ни cron, ни импорт, ни какой-либо
автоматический механизм историю курсов не ведут.

### 1.2 Как курс применяется

`src/lib/fx.ts`, три функции:

```ts
buildRateMap(rows, base)  // берёт по каждой валюте строку с МАКСИМАЛЬНЫМ rate_date
toBase(minor, cur, rates) // r = rates[cur]; if (r === undefined) return minor;  ← 1:1
missingRates(...)         // список валют без курса — НЕ ВЫЗЫВАЕТСЯ НИГДЕ
```

Пересчёт выполняется **только в TypeScript в момент рендера страницы**. В БД не
попадает ни курс, ни результат. Отсюда два следствия, зафиксированные ещё в
аудите: отчёт за прошлый месяц меняется при обновлении курса (FIN-02), а валюта
без курса молча считается как рубль (FIN-01).

### 1.3 Интеграция с ЦБ РФ (что есть сейчас)

| Место | Что делает |
|---|---|
| `src/lib/cbr.ts` | `GET https://www.cbr-xml-daily.ru/daily_json.js` — **только курсы на сегодня**, исторического запроса нет. Делит `Value / Nominal`. **Единственное место, где уже реализовано `USDT ← USD`** |
| `src/app/api/cbr/route.ts` | прокси того же URL для клиента |
| `RatesEditor` → «Курс ЦБ на сегодня» | подставляет значения в форму; пользователь сохраняет их в `fx_rates` с `rate_date = сегодня` |
| `src/app/(app)/transactions/page.tsx:181-189` | **единственная страница**, которая подмешивает курсы ЦБ на сегодня для валют, которых нет в `fx_rates` |

То есть страница «Операции» и все остальные страницы сегодня считают
мультивалютные суммы **по-разному**.

## 2. Что использует LATEST rate

Все места, где вызывается `buildRateMap` + `toBase` (курс — последний введённый,
дата операции не учитывается):

`dashboard`, `transactions` (KPI), `reports`, `reports/pnl`, `reports/cashflow`,
`projects/[id]`, `employees` (список), `employees/[id]`, `counterparties/[id]`,
`agents`, `payroll`, `debts`, `calendar`, `budgets`, `accounts` (`AccountsList`),
`DrilldownModal`, `EditableTransactionRow`, `LinkPaymentButton`,
`src/lib/unallocated.ts`, `src/lib/alerts.ts` (уведомления и cron-дайджест).

## 3. Что использует ИСТОРИЧЕСКИЙ rate

**Ничего.** Ни одного места. Исторических курсов в системе нет в принципе:
в `fx_rates` одна строка, а запрос к ЦБ умеет только «на сегодня».

## 4. Что использует fallback 1:1

`toBase()` возвращает сумму без изменений для любой валюты, которой нет в карте
курсов. Это касается **всех** потребителей из §2, кроме страницы «Операции»,
которая сначала подмешивает курсы ЦБ на сегодня.

Сегодня в `fx_rates` есть только `USDT`. Значит **любая операция в USD, EUR, CNY,
GBP, KZT, UAH была бы посчитана как рубли 1:1** — молча, без предупреждения
(`missingRates()` написан, но не вызывается).

## 7. CBR COVERAGE

ЦБ РФ публикует официальный курс к рублю для всех валют справочника, **кроме USDT**:

| Код | Котируется ЦБ | Номинал в выгрузке ЦБ | Есть в данных после cutover |
|---|---|---|---|
| USD | **да** | 1 | нет (но нужен как база для USDT) |
| EUR | да | 1 | нет |
| CNY | да | 1 | нет |
| GBP | да | 1 | нет |
| KZT | да | **100** | нет |
| UAH | да | **10** | нет |
| RUB | базовая, курс = 1 | — | да |
| **USDT** | **нет** (криптоактив, ЦБ не котирует) | — | **да, 34 операции** |

Номинал критичен: курс = `Value / Nominal`. `lib/cbr.ts` это уже делает, но при
переходе на историю правило надо сохранить и хранить `nominal` в котировке.

### Источники исторических котировок

| Источник | Endpoint | Комментарий |
|---|---|---|
| ЦБ РФ (официальный) | `https://www.cbr.ru/scripts/XML_daily.asp?date_req=DD/MM/YYYY` | первоисточник, XML, cp1251; возвращает курсы, **действующие на указанную дату** |
| ЦБ РФ, динамика одной валюты | `XML_dynamic.asp?date_req1=..&date_req2=..&VAL_NM_RQ=R01235` | удобно для разового бэкофилла USD |
| cbr-xml-daily.ru (зеркало, уже используется) | `/daily_json.js` (сегодня), `/archive/YYYY/MM/DD/daily_json.js` (на дату) | JSON, проще в обработке, но это **не первоисточник** |

Рекомендация: тянуть с официального `cbr.ru`, зеркало оставить резервом, и в
каждой котировке хранить, откуда она пришла (`fx_source`).

## 8. USDT / UNSUPPORTED CURRENCY PROPOSAL

Правило (утверждено): **1 USDT = 1 USD**, далее официальный USD/RUB ЦБ на дату
операции.

```
rub_amount = usdt_amount × CBR_USD_RUB(operation_date)
```

Сохраняется/восстанавливается для каждой операции:

| Поле | Пример для операции 1 000 USDT от 25.08.2026 |
|---|---|
| `original_amount` | 100000 (минорные) |
| `original_currency` | `USDT` |
| `fx_base_currency` | `USD` |
| `fx_rate` | курс USD/RUB ЦБ, действующий на 25.08.2026 |
| `fx_rate_date` | дата котировки, которая реально применена (для выходных — дата последней котировки, действующей на эту дату) |
| `fx_source` | `CBR` |
| `fx_method` | `USDT_USD_1_TO_1_CBR` |
| `rub_amount` | `round(1000 × fx_rate)` в минорных |

Для остальных валют:

| Валюта | Метод | `fx_base_currency` |
|---|---|---|
| RUB | `IDENTITY`, `fx_rate = 1` | RUB |
| USD, EUR, CNY, GBP, KZT, UAH | `CBR_DIRECT`, курс на дату с учётом номинала | сама валюта |
| любая другая / нет котировки | **`FX_RATE_MISSING`** | — |

`FX_RATE_MISSING` — это **статус операции**, а не ноль и не 1:1:

* операция сохраняется и видна в реестре (импорт не блокируется);
* `base_amount` = `NULL`;
* в любую сумму в базовой валюте такая операция **не включается**, а выводится
  отдельной строкой «не пересчитано: N операций на X USDT» с ссылкой на них;
* `NULL` нигде не должен молча превращаться в 0 — это отдельный тест.

## 9. CUTOVER DESIGN

### 9.1 Два новых объекта

**(а) Таблица котировок — неизменяемая история, общая для всех команд**

```sql
create table fx_quotes (
  source        text not null default 'CBR',   -- CBR | CBR_MIRROR | MANUAL
  quote_currency text not null,                -- USD, EUR, ...
  base_currency  text not null default 'RUB',
  rate_date      date not null,                -- дата, С КОТОРОЙ курс действует
  rate           numeric(18,8) not null check (rate > 0),
  nominal        integer not null default 1,
  fetched_at     timestamptz not null default now(),
  raw            jsonb,                        -- ответ источника как есть
  primary key (source, base_currency, quote_currency, rate_date)
);
```

Котировки ЦБ одинаковы для всех — таблица **не** привязана к команде (в отличие
от текущей `fx_rates`). Строки только добавляются, существующие не правятся.

**(б) Разрешение курса «действующего на дату» (weekend/holiday semantics)**

```sql
create function fx_rate_on(_currency text, _date date) returns ... as $$
  select rate/nominal, rate_date
    from fx_quotes
   where quote_currency = _currency and base_currency = 'RUB' and source = 'CBR'
     and rate_date <= _date
   order by rate_date desc limit 1
$$;
```

ЦБ устанавливает курс, который действует **с даты публикации до следующей**.
В выходные и праздники новая котировка не выходит — действует последняя. Правило
`max(rate_date) <= operation_date` даёт ровно это и, в отличие от обращения к
внешнему API на каждую дату, **воспроизводимо офлайн**. Для семи USDT-дат на
выходных из §6 будет применён курс ближайшей предшествующей рабочей даты.

Отдельно нужен guard: если для валюты нет ни одной котировки с `rate_date <= D`
(например, дата раньше начала загруженной истории) — это `FX_RATE_MISSING`,
а не «взять первую попавшуюся».

### 9.2 Фиксация курса на операции — ключ к воспроизводимости

Отчёты **не должны** пересчитывать курс. Курс применяется один раз при записи
операции и хранится вместе с ней:

```sql
alter table transactions
  add column fx_status        text not null default 'legacy'   -- ok | missing | legacy
      check (fx_status in ('ok','missing','legacy')),
  add column fx_base_currency text,          -- USD для USDT, сама валюта для прочих
  add column fx_rate          numeric(18,8), -- 1 единица валюты = fx_rate RUB
  add column fx_rate_date     date,          -- дата котировки, реально применённой
  add column fx_source        text,          -- CBR
  add column fx_method        text,          -- IDENTITY | CBR_DIRECT | USDT_USD_1_TO_1_CBR
  add column base_amount      bigint;        -- сумма в базовой валюте, минорные
```

* `fx_status='legacy'` — операции до cutover: ничего не пересчитываем, отчёты по
  ним работают как сейчас;
* `fx_status='ok'` — курс зафиксирован, `base_amount` заполнен;
* `fx_status='missing'` — курс определить не удалось, `base_amount is null`.

Инвариант: `fx_status='ok'` ⟺ `base_amount is not null and fx_rate is not null`
(CHECK-ограничение).

**Когда фиксируется:** при создании операции и при изменении `amount`,
`currency` или `occurred_on` — то есть внутри уже существующих RPC
(`transaction_insert`, `transaction_save`, `bank_import_commit`,
`obligation_pay`, `transaction_split`, `transactions_merge_transfer`). Отдельным
триггером `before insert or update of amount, currency, occurred_on` это делается
надёжнее, чем вызовами из кода: ни один путь записи не сможет «забыть» FX.

**Почему именно так, а не «считать на лету по дате»:** пересчёт на лету снова
сделает отчёт зависимым от содержимого таблицы котировок (задним числом
поправили/дозалили котировку — цифры поехали). Требование «расчёт за 25.08.2026
через месяц должен дать тот же результат» выполняется только фиксацией
результата на строке.

### 9.3 Split: FX применяется один раз

`transaction_lines` расширяется так, чтобы часть **наследовала** курс операции:

```sql
-- в представлении:
case when t.base_amount is null then null
     when s.id is null then t.base_amount
     else round(t.base_amount::numeric * s.amount / nullif(t.amount,0))::bigint
end as base_amount,
t.fx_rate, t.fx_rate_date, t.fx_source, t.fx_method, t.fx_status
```

Никакого повторного обращения к курсам. Проверяемый инвариант:
`Σ base_amount строк операции = transactions.base_amount`.

⚠ Округление: при пропорциональном делении сумма частей может разойтись с целым
на ±1 копейку (например, 1 000 USD × 78,4321 ₽ при делении 60/40). Нужен метод
наибольших остатков: последней части отдаётся остаток
`base_amount − Σ уже распределённого`. Это нельзя выразить простым `round()` в
представлении — потребуется оконная функция или материализация. Это единственное
место дизайна, где я рекомендую отдельный прототип и тест до реализации.

### 9.4 Что делать с остальными слоями

| Объект | Предложение |
|---|---|
| `obligation_payments` | добавить `currency`, `fx_rate`, `base_amount`. Сейчас колонки валюты нет вообще, а триггер `settle_obligation_on_tx` кладёт туда сумму **в валюте операции** в обязательство, которое может быть в другой валюте. После cutover это надо сделать явным |
| `invoices` | зафиксировать FX на `issue_date` (те же поля). Вопрос к бизнесу: по дате выставления или по дате оплаты. **Требует вашего решения** |
| `obligations` | зафиксировать FX на `period_month`/`due_date` — это начисление, отдельное экономическое событие от оплаты |
| `fx_rates` (текущая) | оставить как ручной источник для legacy-периода; после cutover она в расчёте post-cutover операций не участвует |
| `toBase()` / `buildRateMap()` | остаются только для legacy-периода. Для post-cutover отчёты читают `base_amount` |
| `missingRates()` | заменяется на честный статус `fx_status='missing'` |

а не миграция на миллионы строк.

Отдельно: **бэкофилл — это изменение исторических данных**. По вашему же правилу
он делается отдельным подтверждённым шагом, с dry-run BEFORE/AFTER, как это
сделано для FIN-03.

## 11. EXPECTED IMPACT ON REPORTS

Текущее состояние: весь USDT после cutover оценён по **единственному курсу
80,00 ₽ от 16.06.2026**.

| Показатель | Сейчас |
|---|---|
| USDT-оборот после cutover | 12 068,00 USDT |
| его оценка в отчётах | 12 068 × 80 = **965 440,00 ₽** |
| доля в обороте периода | 965 440 из ≈ 3 975 796 ₽ ≈ **24 %** |

После перехода каждая из 34 операций получит курс своей даты. Точную дельту
можно назвать только после загрузки котировок — придумывать её я не буду.
Чувствительность считается прямо:

> отклонение среднего фактического курса USD/RUB от 80,00 ₽ на **1 ₽** меняет
> оценку периода на **12 068 ₽**; на 5 ₽ — на **60 340 ₽**.

Что изменится качественно:

1. **Исторические отчёты замрут.** Сейчас правка `fx_rates` меняет цифры за все
   прошлые месяцы; после — прошлое фиксировано.
2. **Страница «Операции» перестанет расходиться с остальными** (сейчас только она
   подмешивает курс ЦБ на сегодня).
3. **Остатки счетов в USDT** начнут считаться по курсу каждой операции, а не по
   одному курсу на всё; остаток валютного счёта **в самой валюте** не изменится.
4. **«Нераспределённые выплаты»** (`unallocated.ts`) перестанут «плавать»: сейчас
   остаток разнесения пересчитывается текущим курсом, и операция может то
   появляться, то исчезать из списка при смене курса.
5. **Появится статус `FX_RATE_MISSING`** — операции, которые раньше молча
   считались 1:1, станут видимой проблемой. На текущих данных таких нет
   (есть только RUB и USDT), но правило начнёт защищать сразу.
6. Отчёт, пересекающий 20.08.2026, будет содержать **два режима** оценки. Это
   нужно явно показывать в интерфейсе, иначе выглядит как ошибка.

## 12. RISKS

| # | Риск | Комментарий / смягчение |
|---|---|---|
| R1 | **Округление при split.** Пропорциональное деление `base_amount` может дать расхождение ±1 копейка | метод наибольших остатков; инвариант `Σ base_amount частей = base_amount операции` как тест и как ограничение |
| R2 | **Зависимость от внешнего источника.** `cbr-xml-daily.ru` — зеркало, не первоисточник; может отстать или исчезнуть | грузить с `cbr.ru`, зеркало — резерв; в каждой котировке хранить `source`; отсутствие котировки = `FX_RATE_MISSING`, а не тихий пропуск |
| R3 | **`1 USDT = 1 USD` — бизнес-соглашение, а не рынок.** Реальные отклонения USDT/USD (±0,5 %) в учёте не отражаются | зафиксировано в `fx_method`; при необходимости позже можно ввести отдельный источник котировок USDT |
| R4 | **Номинал валют.** KZT — 100, UAH — 10 | хранить `nominal` в котировке и делить; тест на KZT/UAH даже без данных в проде |
| R5 | **Правка операции задним числом.** Смена даты/суммы/валюты обязана перефиксировать FX | триггер на `before update of amount, currency, occurred_on`, а не вызовы из кода |
| R6 | **Два режима в одном отчёте** (legacy до 20.08 и pinned после) | явная пометка в UI; период отчёта целиком до или целиком после — предпочтительный сценарий |
| R7 | **`obligation_payments` без валюты** — уже сейчас несогласовано: триггер `settle_obligation_on_tx` кладёт сумму в валюте операции в обязательство другой валюты. После cutover это станет заметнее | 1 такая операция после cutover; требует решения вместе с M7 |
| R8 | **Бэкофилл меняет исторические цифры** за уже закрытые периоды (август–сентябрь 2026) | отдельный подтверждённый шаг с dry-run BEFORE/AFTER; при необходимости — только вперёд, без пересчёта уже сданной отчётности |
| R9 | **Нагрузка на путь записи.** FX-триггер добавляет обращение к `fx_quotes` на каждую вставку операции | индекс `(quote_currency, rate_date desc)`; при импорте выписки — один справочник на батч |
| R10 | **Курс за «сегодня» ещё не опубликован.** ЦБ публикует курс на следующий рабочий день около 15:30 МСК | правило `max(rate_date) <= D` это покрывает: до публикации действует предыдущий курс. Но операция «сегодняшней» датой, созданная до публикации, зафиксирует предыдущий курс — нужно решить, допустимо ли это, или такие операции пере-фиксировать вечером |
