### Какой механизм приложения создал каждую запись

| Запись | Механизм | Доказательство |
|---|---|---|
| A (`transfer`) | Импорт выписки Точки — `src/lib/tochka-import.ts`. Внутренний перевод **склеивается в одну строку** `type='transfer'` (`tochka-import.ts:41-42, 92-98`: оставляется только Debit-нога, ставится `transfer_account_id` по `bank_account_links`) | `source='tochka'`, `external_id` = id операции в банке, 56 строк привязаны к батчам `Точка …` от 2026-06-25 (15:03…21:56 UTC, отдельный батч на счёт) |
| B (`expense`) + C (`income`) | Импорт сводной выписки — `src/components/StatementImportWizard.tsx`. В нём **переводы намеренно не склеиваются**: комментарий батча, который пишет сам код, — «Импорт сводной выписки (Все операции), **переводы не склеиваются**» (`StatementImportWizard.tsx:253-261`) | обе записи в батче `svodnaya_vypiska_2025.csv`; `source`/`external_id` не заполняются — **grep по обоим визардам даёт 0 совпадений** для `source:` и `external_id` |

Итог: **A — банковское представление события, B+C — CSV-представление того же события.**
Экономическое событие одно, проводок — две. Это и есть двойное отражение.

### Почему это не LEGITIMATE_PAIR

Отвергнутая альтернатива «в один день прошли два одинаковых перевода на одну сумму с одинаковым
описанием»: при таком сценарии на каждый transfer нашлось бы 2+ кандидата, либо один и тот же
expense «обслуживал» бы два transfer'а. Фактически соответствие строго 1:1:1 при 126 различных
`external_id`, то есть **126 различных банковских событий** — и ровно 126 CSV-пар, ни одной лишней,
ни одной недостающей.

## 3. Root cause

### Гипотеза заказчика — подтверждена, с одной поправкой

Проверялось: «ручные операции → первый импорт Точки → импорт не распознал существующие ручные
операции → две записи одного события».

**Подтверждено. Поправка:** это были не ручные операции, а **импорт CSV сводной выписки**.

Точный механизм:

1. **2026-06-22 21:46:56 UTC** — импорт `svodnaya_vypiska_2025.csv` через `StatementImportWizard`.
   Записи получают `source = NULL`, `external_id = NULL` (визард эти поля **не заполняет**), и
   внутренний перевод сохраняется **двумя** строками: `expense` + `income` («переводы не
   склеиваются» — прямая цитата из note батча, который пишет сам код).
2. **2026-06-25 15:03–21:56 UTC** — первые импорты выписки Точки, отдельным батчем на каждый
   счёт (`Точка 2022-06-01 — 2026-06-25`, `Точка 2023-01-01 — 2026-06-25`, …). Тот же период,
   те же события.
3. Дедуп в `tochka-import.ts:48-52`:
   ```
   .eq("team_id", teamId).eq("source", "tochka").in("external_id", ids)
   ```
   — фильтр по `source='tochka'` и `external_id`. **CSV-строки не имеют ни того, ни другого,
   поэтому для дедупа они невидимы в принципе.**
4. Импорт Точки склеивает внутренний перевод в одну строку `type='transfer'` → рядом с уже
   существующей CSV-парой появляется третья запись того же события.

Уникальный индекс `transactions_source_external_uidx (team_id, source, external_id) where
external_id is not null` ловит только повторный импорт **того же источника**. Между источниками
он не защищает вообще — `NULL` в `external_id` выводит строку из-под индекса.

### Временная граница и почему всё прекратилось после 16.03.2025

Граница задаётся **не банком и не кодом, а содержимым CSV**. Выжившие строки батча
`svodnaya_vypiska_2025.csv` распределены так:

| Месяц | income | expense |
|---|---:|---:|
| 2025-01 | 40 | 38 |
| 2025-02 | 56 | 57 |
| 2025-03 | 48 | 42 |
| 2025-04 … 2025-12 | **0** | 11 |

**Дубль требует обе ноги** (`expense` на счёте-источнике и `income` на счёте-получателе).
`income`-строк в батче нет ни одной после **2025-03-16** — поэтому после этой даты пара не
складывается и дубли исчезают. Это артефакт состава CSV (и/или того, что часть строк батча не
была импортирована: `row_count` = 4702 против 292 фактически существующих строк — визард пишет
в `row_count` число разобранных строк файла, а не вставленных), а не следствие исправления кода.

### Может ли повториться сегодня — **ДА**

Ни одно из четырёх условий не устранено:

1. `StatementImportWizard.tsx` и `ImportWizard.tsx` по-прежнему **не заполняют** `source` и
   `external_id` (grep: 0 совпадений).
2. Дедуп Точки по-прежнему ограничен `source='tochka'`.
3. В БД **нет ограничения**, запрещающего две проводки одного банковского события.
4. Сверка «CSV ↔ уже импортированное» есть только в `ImportWizard` (режим reconcile, по
   встречным операциям), в `StatementImportWizard` её нет; выбор визарда за пользователем.

Сценарий воспроизведения (**не запускался**, production не изменялся): импортировать CSV за
период, уже загруженный из Точки, — внутренние переводы задвоятся тем же способом. Любой новый
CSV-импорт «за прошлый год для полноты картины» воспроизводит FIN-03.
