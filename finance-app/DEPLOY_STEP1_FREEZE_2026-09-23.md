## 3. Доказательство: Vercel cron больше не выполнит финансовый sync — **НЕТ, не доказано**

Отключить Vercel cron доступными мне средствами **нельзя**:

* `mcp__Vercel__update_project` не имеет поля отключения cron;
* `crons` заданы в `vercel.json` → изменение требует **деплоя** (сейчас запрещён);
* `filter_project_envs` → `403 Forbidden` (нет права листать env проекта),
  т.е. состояние `CRON_SECRET` я подтвердить не могу, а его смена всё равно
  требует redeploy, чтобы попасть в рантайм функций.

Фактический состав Vercel cron (`vercel.json`) — **уточнение к PRECHECK**:

| Путь | Расписание UTC | Пишет финансы? |
|---|---|---|
| `/api/tochka/cron` | `0 5 * * *` | **ДА** — импорт выписки Точки за 45 дней |
| `/api/cron/notifications?mode=digest` | `0 6 * * *` | нет (`notifications`, `notification_prefs`) |
| `/api/cron/recurring` | `0 7 * * *` | **нет** — это `academy_reissue` (повторное обучение), не регулярные операции |
| `/api/cron/notifications?mode=refresh` | `0 8 * * *` | нет |

> Поправка: в PRECHECK `/api/cron/recurring` числился финансовым писателем. Это неверно —
> код маршрута работает только с `academy_assignments`. Регулярные операции
> (`recurring_rules` → `transactions`) материализуются **вручную** из `RecurringManager.tsx`,
> крона для них нет.

Итого финансовый Vercel cron ровно один — `/api/tochka/cron`, **ближайший запуск
2026-09-24 05:00 UTC** (сегодняшний слот уже прошёл). Окно развёртывания сегодня
в этот запуск не попадает, но гарантии отключения нет.

**Требуется действие владельца проекта (одно из двух):**

1. Vercel → проект `basa-16bf` → Settings → Cron Jobs → **Disable** (без деплоя, обратимо); или
2. убрать блок `crons` из `vercel.json` — требует деплоя.

## 4. Обнаружено при проверке: остановка cron **не останавливает** финансовый импорт

Это главный результат шага, он меняет план окна обслуживания.

**4.1. pg_cron `tochka-autosync` уже был неработоспособен.** Задача дёргает
`https://basefinance.pro/api/tochka/cron` с **захардкоженным** Bearer-токеном в теле
команды cron. `net._http_response` показывает, что оба последних вызова вернули
**401 Unauthorized**:

```
id  | status_code | created                        | body
----+-------------+--------------------------------+------------------------
177 |         401 | 2026-09-23 06:00:00.282853+00  | {"error":"Unauthorized"}
176 |         401 | 2026-09-23 03:00:00.263525+00  | {"error":"Unauthorized"}
```

То есть токен в cron-команде не совпадает с текущим `CRON_SECRET` проекта.
Согласуется с тем, что таблица `tochka_sync_log` **пуста (0 строк)** при
`rolbypassrls = true`: маршрут `/api/tochka/cron` не доходит до строки журнала —
он отбивается на проверке `Authorization` раньше. Журнала прогонов синка в БД,
таким образом, **нет вообще**; доказательства прогонов приходится брать из
`bank_connections.last_synced_at`, `import_batches` и `cron.job_run_details`.

**4.2. Реальный источник записей — авто-синк под сессией пользователя.**
`src/components/TochkaAutoSync.tsx` смонтирован в `src/app/(app)/layout.tsx:134`
для **каждого** пользователя с правом редактировать финансы и стреляет
`POST /api/tochka/auto-sync` **при каждом открытии приложения**
(тротлинг: вкладка 30 мин, сервер 120 мин на команду через `bank_sync_claim`).
Этот путь **не требует ни pg_cron, ни Vercel cron, ни `CRON_SECRET`**.

Именно он записал сегодняшний батч: `import_batches` max `created_at` =
**06:04:03.838 UTC**, `bank_connections.last_synced_at` = **06:04:07.772 UTC**,
тогда как pg_cron в 06:00:00 получил 401. Прогон в 06:04 — открытие приложения живым
пользователем.

**Вывод:** после выполнения Разрешения №1 финансовые записи в production
**по-прежнему возможны** — достаточно, чтобы любой сотрудник с ролью
редактирования финансов открыл `basefinance.pro`. Это не побочный риск, а основной
канал импорта. Разрешение №1 закрывает `bybit-sync-daily` (он реально работал,
`select public.bybit_sync_logged(7)` в БД) и формально `tochka-autosync` (который
и так возвращал 401), но не закрывает авто-синк.

Варианты закрытия — **ни один не выполнен, требуется отдельное разрешение**:

| Вариант | Что делает | Нужен деплой | Обратимость |
|---|---|---|---|
| A. Организационный | попросить команду не открывать приложение в окне | нет | полная |
| B. `bank_connections` | временно снять/переименовать запись `provider='tochka'` → маршрут вернёт `not_connected` | нет | требует аккуратного восстановления `token_cipher` |
| C. Vercel Firewall | deny-правило на `/api/tochka/auto-sync` и `/api/tochka/cron` | нет | полная (снять правило) |
| D. Vercel Pause Project | приложение недоступно целиком | нет | полная |

Вариант C дополнительно закрывает и незакрытый п.3 (Vercel cron).

## 7. Новая находка вне объёма PR #99

**OPS-01 (MEDIUM).** Секрет `CRON_SECRET` хранится **в открытом виде** в теле команды
`cron.job` (`jobid = 2`) — читается любым, кто имеет доступ к схеме `cron`. Значение
при этом **устарело** (401), поэтому задача была холостой. Требует ротации секрета и
переноса значения в `vault`/`app.settings` при последующем включении. В PR #99 не входит.

**OPS-02 (LOW).** `tochka_sync_log` пуст — журнала автоимпорта в БД фактически нет,
хотя мониторинг после развёртывания в runbook на него опирается. Раздел мониторинга
`PRODUCTION_DEPLOY_RUNBOOK.md` надо переориентировать на `import_batches` +
`bank_connections.last_synced_at`.
