## 1. Bank event identity — блокер подтверждён и устранён

### Что показал collision analysis на всей истории production

Отпечаток первой версии 0090 — `team|account|date|amount|currency|direction`:

| Метрика | Значение |
|---|---|
| Групп отпечатка среди банковских строк | 6 931 |
| **Групп с коллизией** | **537** |
| Строк, попавших в коллизии | 1 164 |
| «Лишних» строк, которые правило кратности могло пропустить | **627** |
| **Групп, где 2+ РАЗНЫХ `provider transaction id`** | **446** |
| Групп, различающихся только назначением платежа | 368 |
| Групп, различающихся только контрагентом | 20 |

446 групп — это заведомо **разные реальные операции** (у них разные идентификаторы
в банке), которые первая версия правила кратности при следующем импорте могла
молча пропустить. Это silent loss финансовой операции → первая версия 0090 была
**NO-GO**, и она переписана.

Усиление отпечатка контрагентом и назначением платежа проблему не снимает:

| Отпечаток | Групп с коллизией | Из них с 2+ provider id |
|---|---|---|
| + контрагент + первые 40 симв. назначения | 238 | 112 |
| + первые 80 | 71 | 71 |
| + первые 120 | 5 | 5 |
| + ПОЛНОЕ назначение | 2 | **2** |
| + контрагент + нормализованное назначение (итоговая формула) | 201 | **75** |

Остаются **75 групп**, неразличимых даже по полному описанию. Пример из
production: два вывода Bybit 2026-05-13 на 100,00 USDT с одинаковым текстом
«Bybit вывод USDT» и разными id `bybit-wd-226074267` / `bybit-wd-226100544`.

**Вывод: инъективного отпечатка на этих данных не существует.** Отпечаток не может
быть основанием для пропуска операции, у которой есть идентификатор провайдера.

### Реализованный приоритет идентичности (0090 v2)

1. `bank_event_id` = `provider : provider account : provider transaction id`
   (generated column, уникален в команде) — **единственный** признак, по которому
   кандидат с id провайдера может быть пропущен.
2. `bank_event_fp_strong` = счёт · дата · сумма · валюта · направление · контрагент ·
   **нормализованное** назначение — только для кросс-импортной сверки.
   Нормализация (`bank_note_norm`): отрезать хвост после `·`
   («Платежное поручение №…»), оставить буквы и цифры, привести к нижнему регистру.
   Замер на production: даёт совпадение **130 из 130** известных кросс-импортных
   пар FIN-03 — то есть достаточна для сверки без произвольной длины префикса.
3. `bank_event_fp` (слабый) — для индексирования и обнаружения неоднозначностей.

Правила `bank_import_commit`:

| # | Условие | Действие |
|---|---|---|
| 1 | есть `bank_event_id`, такой уже есть в БД | пропуск (дубль по id провайдера) |
| 2 | есть `bank_event_id`; ровно 1 кандидат и ровно 1 существующая строка без id провайдера с тем же сильным отпечатком | **повышение** существующей строки до канонической банковской |
| 3 | есть `bank_event_id`, сопоставление не 1:1 | **вставка** + запись в журнал сверки (`ambiguous_match`) |
| 4 | нет `bank_event_id` (CSV); ровно 1 кандидат и ровно 1 существующая строка | пропуск + запись в журнал (`auto_merged`) |
| 5 | нет `bank_event_id`, совпадений нет | вставка |
| 6 | нет `bank_event_id`, сопоставление не 1:1 | **вставка** + запись в журнал (`ambiguous_duplicate`) |

Ни одна операция не удаляется и не пропускается молча: любой пропуск по
отпечатку журналируется в `bank_reconciliation_conflicts` вместе с полным
payload кандидата, поэтому решение видно и обратимо. Неоднозначность никогда
не приводит к автоматическому склеиванию — только к вставке и конфликту.

## 3. Авторизация SECURITY DEFINER функций

### SEC-008 (HIGH) — найдено при этом ревью, существует в production сейчас

`can_edit_finance() / can_write_tx() / can_manage_team()` возвращают **NULL** для
того, кто не состоит в команде (`role in (...)` при `role IS NULL`). Для RLS это
отказ. Но в plpgsql `if not can_edit_finance(t) then raise` при NULL **не
срабатывает** — защита молча пропускает вызывающего.

Проверено на production (только чтение): `auth.uid() = NULL` →
`can_edit_finance(team) = NULL`, `(not can_edit_finance(team)) IS NULL = true`.

Такой guard стоит в **6** функциях: `support_open_period`, `support_delete_period`,
`merge_counterparties`, `materialize_auto_accruals`, `materialize_support_cycles`,
`academy_assign`. При этом `support_open_period` и `support_delete_period` имеют
EXECUTE у **PUBLIC и anon**, а они пишут в `project_periods`, `obligations` и
`transactions`.

Эмпирическое подтверждение (disposable DB, режим `pre`): пользователь, не
состоящий ни в одной команде, вызвал `support_open_period` для проекта чужой
команды — вызов **прошёл** и создал период (1 → 2). В режиме `post` тот же вызов
получает «Недостаточно прав», данные не меняются.

Исправление (0091) сделано в одном месте — в самих хелперах (`exists(...)` вместо
`role in (...)`), поэтому защищены все вызывающие, включая ещё не написанные.
Дополнительно сняты EXECUTE у anon/PUBLIC с пяти функций, которые пишут данные
(проверено grep'ом: приложение их из анонимного контекста не вызывает).

### Матрица проверки новых RPC

Для каждой новой функции: `SECURITY DEFINER` + `set search_path = public`,
EXECUTE только `authenticated` (у `is_service_role` — плюс `service_role`),
`op_begin`/`op_finish` клиенту не выданы вовсе.

| RPC | Кто может вызвать | Проверка команды | Проверка роли | Исключение service_role |
|---|---|---|---|---|
| `invoice_save` | authenticated | команда берётся у существующего инвойса, иначе из payload; контрагент/проект проверяются на принадлежность | `can_edit_finance` | нет |
| `obligation_allocate` | authenticated | команда из обязательства; операция проверяется на ту же команду | `can_edit_finance` | нет |
| `transaction_split` / `transaction_save` / `transaction_delete` | authenticated | команда из самой операции | `can_modify_tx` (финансовые роли или employee-владелец) | нет |
| `transactions_merge_transfer` / `transaction_match_planned` | authenticated | обе операции обязаны быть одной команды | `can_edit_finance` | нет |
| `transactions_bulk_patch` | authenticated | все id обязаны быть одной команды; справочники проверяются | `can_write_tx`; для `account_id`/`status` — `can_edit_finance`; плюс `can_modify_tx` на каждую строку | нет |
| `transactions_convert_to_transfer` | authenticated | все id одной команды; счёт проверяется | `can_edit_finance` | нет |
| `transaction_insert` | authenticated | `team_id` из payload проверяется по ролям; все ссылки — на принадлежность | `can_write_tx` | нет |
| `obligation_pay` | authenticated | команда из обязательства; счёт проверяется | `can_edit_finance` | нет |
| `bank_import_commit` | authenticated | счёта кандидатов проверяются на принадлежность команде | `can_edit_finance` **или** `is_service_role` | да (Vercel-cron) |
| `bank_sync_claim` | authenticated | по `team_id` + provider | то же | да |
| `is_service_role` | authenticated | — | роль берётся из проверенных claim'ов JWT PostgREST; клиент подменить не может | — |
| `can_modify_tx` | authenticated | команда из операции | NULL-safe | — |
| `op_begin` / `op_finish` | **никто** (revoke all from public) | вызываются только изнутри других функций | — | — |

### Результат атак «команда A → объект команды B»

21 проверка, все PASS: `invoice_save`, `obligation_allocate`, `transaction_split`,
`transaction_save`, `transaction_delete`, `transactions_bulk_patch`,
`transactions_convert_to_transfer`, `transaction_insert`, `bank_import_commit`,
`bank_sync_claim` — отказ; посторонний (не участник) — отказ; `viewer` своей
команды — отказ на запись; `can_modify_tx` — `false` на чужую операцию и `true` на
свою; `is_service_role` — `false` для клиента; `op_begin` — `permission denied`.
Снимок данных команды B (операции / разнесения / позиции / оборот / периоды)
до и после всех попыток **идентичен**.

Ошибка, найденная этим тестом и исправленная до отправки: в
`transactions_bulk_patch` и `transactions_convert_to_transfer` использовался
`min(team_id)` — такой агрегат для `uuid` в Postgres не существует, функция падала
до проверки прав. Заменено на отдельный запрос.

**Обратное направление несовместимо:** новый код требует RPC из 0088–0091 и
колонки `transactions.version`. Поэтому деплой — «сначала БД, потом код», а
откат — «сначала код, потом (если нужно) БД». Откатывать миграции при работающем
новом коде нельзя.

Особые случаи:
* `0087_down` не восстанавливает прежние тела `materialize_auto_accruals` /
  `materialize_support_cycles` автоматически — их текст нужно сохранить **до**
  деплоя (`pg_get_functiondef`), иначе откат неполный. Это записано в runbook как
  обязательный шаг PRECHECK.
* `0088_down` удаляет `operation_requests` — после этого повторная отправка тех же
  форм снова может создать дубли.
* `0090_down` удаляет `bank_reconciliation_conflicts` — выгрузить, если конфликты
  уже разбирались.
* Откат 0091 возвращает SEC-008. Делать только вместе с отказом от 0091 целиком.

## 6. Бизнес-требование: одна операция — несколько проектов/сотрудников/статей

### Как это устроено сейчас

В приложении **два разных** механизма, и их важно не путать:

| Механизм | Что делает | Таблицы | Это то, что нужно по требованию? |
|---|---|---|---|
| **«Части операции»** (`TransactionPartsEditor`) | операция остаётся **ОДНОЙ** строкой; части лежат отдельно и несут свои `project_id`, `counterparty_id`, `category_id`, `note` | `transactions` + `transaction_splits` | **да** |

То есть **T9 и требование про 60/40 — про разные механизмы**, и изменения T9
механизм «частей» не затрагивают.

### SPLIT-01 (MEDIUM) — нарушение требования, существующее ДО PR #99

`transaction_splits` читают только три места: бейдж «split» в списке операций,
**ОПиУ** и **ДДС**. Страницы **проекта**, **сотрудника** и **контрагента** берут
суммы напрямую из `transactions` по `project_id` / `counterparty_id` и части
**не учитывают**:

* `src/app/(app)/projects/[id]/page.tsx` — `.eq("project_id", id)`
* `src/app/(app)/employees/[id]/page.tsx` — `.eq("counterparty_id", id)`
* `src/app/(app)/counterparties/[id]/page.tsx` — `.eq("counterparty_id", id)`

Следствие: в примере из требования карточка «Проект A» покажет либо **0**
(если у самой операции `project_id` пуст, как и бывает при разнесении), либо все
**100 000** (если `project_id` операции = A) — но не 60 000. Дашборд считает
месячные доходы/расходы по операциям целиком, поэтому там двойного счёта нет,
но и разбивки по частям тоже нет.

На production это уже проявляется в малом объёме: 2 операции с 4 частями
(25 000 ₽ суммарно), причём **2 части указывают на проект, отличный от
проекта самой операции**, и 2 — на другого контрагента.

**Это не регрессия PR #99** — так было и до него; PR не менял ни одну из этих
страниц. Поэтому в GO/NO-GO по миграциям SPLIT-01 не входит: он не создаёт
ни потери, ни дублирования операции, это неполнота аналитики.

**Предлагаемое изменение (архитектуру заранее не меняю, жду решения):**
завести представление `transaction_lines` — «строки аналитики»: для операции с
частями это её части, для операции без частей — сама операция.

```sql
create view transaction_lines as
select t.id as transaction_id, t.team_id, t.type, t.status, t.currency,
       t.occurred_on, t.accrual_date,
       coalesce(s.amount, t.amount)                   as amount,
       coalesce(s.project_id, t.project_id)           as project_id,
       coalesce(s.counterparty_id, t.counterparty_id) as counterparty_id,
       coalesce(s.category_id, t.category_id)         as category_id,
       s.id as split_id
  from transactions t
  left join transaction_splits s on s.transaction_id = t.id;
```

и перевести на него три страницы (проект, сотрудник, контрагент), а заодно ОПиУ
и ДДС — чтобы правило агрегации было одно и в одном месте. Сумма по
`transaction_lines` для операции всегда равна её сумме ровно один раз, поэтому
двойного счёта это не создаёт. Объём работы — одна миграция + правки трёх
страниц; тесты S2* уже написаны именно под это правило.
